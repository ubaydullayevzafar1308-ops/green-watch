# LEARNING.md — как объяснить Tashkent Green Watch на собеседовании

Документ написан по реальному коду `greenwatch/` и `config.yaml`. Если чего-то в коде нет, это сказано прямо. Цифры взяты из конфига.

---

## 1. Общая картина

**Задача.** По спутниковым снимкам Sentinel-2 (10 м/пиксель) определить, где в Ташкенте зелень (деревья и кустарник), как её доля менялась в 2019–2025 годах, и где зелень пропала или появилась. Результат: карта, где видны гексагоны с долей зелени и участки потерь/прироста.

**Путь данных:**

```
STAC (Planetary Computer, Sentinel-2 L2A + ESA WorldCover)
   │  data/download.py: поиск сцен, маска облаков по SCL, поправка baseline, медианный композит
   ▼
data/raw/s2_{год}.tif (6 бэндов, uint16)   data/raw/wc_{2020,2021}.tif (классы WorldCover)
   │  data/tiles.py: метки green = {10,20}; блоки 512 px + буфер 64 px -> train/val/test; 3 фолда
   ▼
data/tiles/fold{k}/: train = вся сцена + список допустимых кропов, val/test = тайлы 256 (8 каналов: 6 бэндов + NDVI + NDBI)
   │  train.py: U-Net(resnet34), 500 случайных кропов за эпоху, BCE+Dice, порог на val, NDVI-бейзлайн, среднее ± std по фолдам
   ▼
outputs/models/best.pt + metrics.json
   │  infer.py: скользящее окно 256, перекрытие 50%, Hann-окно -> P(green) для каждого года
   ▼
outputs/pred/prob_{год}.tif (uint8 = P*250) + PNG-оверлеи
   │  change.py: гистерезис вокруг порога модели (thr ± 0.15), очистка, векторизация, confirmed
   ▼
outputs/change/{loss,gain}_{A}_{B}.geojson
   │  aggregate.py: H3-гексагоны (res 8), районы (если есть файл), сводка по городу
   ▼
outputs/stats/*.json  ->  api/main.py (FastAPI)  ->  web/ (Leaflet-карта)
```

Команды: `python -m greenwatch download | tiles | train | infer | change | aggregate | pipeline | demo | serve`. Команда `demo` прогоняет весь пайплайн на синтетических данных без интернета.

## 2. Модули по одному

### `config.py`
- `load_config(path, overrides)` читает `config.yaml`, при необходимости накладывает переопределения через `deep_merge` (так работает `demo`: меняет размер тайла, энкодер, пути). Добавляет `cfg["_root"]`.
- `p(cfg, key)` возвращает путь из `cfg["paths"]` и создаёт папку.
- `save_json` / `load_json`; `get_device()` выбирает mps (Mac) -> cuda -> cpu.
- Зачем: все параметры в одном YAML, код не содержит "магических чисел". Эксперимент воспроизводится по одному файлу.

### `raster.py`
- `write_tif` пишет GeoTIFF (deflate, тайлы 256). `read_tif` читает массив, transform, CRS и имена бэндов.
- `apply(transform, col, row)` переводит пиксель в координаты карты (работает и с массивами).
- `to_web_overlay` перепроецирует массив в EPSG:3857 и возвращает границы в lat/lon: так PNG встаёт на Leaflet-карту (`imageOverlay`).
- Зачем: расчёты идут в метрической UTM (EPSG:32642), а веб-карта требует Web Mercator. Пересчёт делается только для показа.

### `features.py`
- `compute_features`: делит uint16 на 10000 (получает отражательную способность), считает индексы и склеивает каналы. Возвращает признаки (C,H,W) и маску `valid` (все бэнды > 0). Невалидные пиксели обнуляются.
- Индексы: NDVI = (B08−B04)/(B08+B04), NDBI = (B11−B08)/(B11+B08). В коде есть ещё NDWI, но в конфиге он не используется (`extra_indices: ["NDVI","NDBI"]`).
- `normalize` — стандартизация по средним и std каналов.
- Зачем индексы, если сеть сама могла бы их выучить: они дают готовый сильный сигнал (NDVI — растительность, NDBI — застройка) и стабилизируют обучение. Каналов получается 6+2 = 8.

### `metrics.py`
- `confusion` считает TP/FP/FN/TN только по пикселям, где метка не равна `IGNORE = 255`.
- `scores`: IoU, F1, precision, recall, accuracy. `evaluate` округляет результат.
- `best_threshold` перебирает пороги 0.05…0.95 с шагом 0.025 и выбирает порог с лучшим F1.
- Зачем: метки с "не знаю" (nodata, облака) не должны ни наказывать модель, ни улучшать метрики.

### `model.py`
- `build_model` создаёт модель из `segmentation_models_pytorch` по имени архитектуры (`Unet`), энкодер `resnet34`, `in_channels=8`, `classes=1` (один логит).
- `save_checkpoint` / `load_checkpoint` сохраняют веса и `meta` (mean/std, список бэндов, индексы, порог, год обучения). Инференс берёт всё из чекпоинта и не зависит от конфига.
- `predict_scene`: инференс скользящим окном (подробнее в разделе 3.8). `_window` строит 2D-окно Ханна.
- Веса ImageNet (`encoder_weights: imagenet`) рассчитаны на 3 канала. Библиотека адаптирует первый слой под 8 каналов. Что именно происходит с весами при этом, в проекте не проверялось, это решает smp.

### `train.py`
- `TileDataset`: нормализация + аугментации (поворот на k·90°, отражение, радиометрический jitter).
- `masked_loss`: маскированный BCE + Dice.
- `channel_stats`: mean/std считаются по train и только по не-ignore пикселям.
- `train()`: AdamW (lr 0.0003, weight_decay 0.0001), косинусное расписание, 15 эпох, batch 16, early stopping с `patience: 4` по val IoU, лучший чекпоинт сохраняется. После обучения подбирается порог на val (`best_threshold`), затем `evaluate_all`.
- `evaluate_all`: на каждом сплите считает метрики U-Net и NDVI-бейзлайна. Сплиты: `val`, `test`, `test_time`.
- MLflow подключается, только если пакет установлен (`_mlflow()`); иначе тихо пропускается.

### `infer.py`
- `main`: для каждого доступного года читает композит, считает признаки, `predict_scene`, пишет `prob_{год}.tif` как uint8 (P×250, 255 = nodata, `prob_to_uint8`).
- `read_prob` читает обратно в float с NaN на nodata.
- `green_overlay` и `rgb_overlay` делают PNG для карты; `index.json` хранит годы, границы и порог.
- Зачем uint8 ×250: файл в 4 раза меньше float32, точность 0.004 для вероятности достаточна, а 255 остаётся для nodata.

### `change.py`
- `hysteresis_thresholds`: high = thr + 0.15, low = thr − 0.15 (ограничение 0.05…0.95), где `thr` — порог модели из чекпойнта (`model_threshold`). При thr = 0.65 получается 0.80 / 0.50.
- `detect`: гистерезис. Потеря = `(p0 >= high) & (p1 <= low)`, прирост наоборот. Учитываются только пиксели, валидные в обоих годах.
- `clean_mask`: `binary_opening` (1 итерация), затем удаление связных компонент меньше `min_area_m2` (500 м² = 5 пикселей по 100 м²).
- `vectorize`: превращает маску в полигоны (`rasterio.features.shapes`), добавляет `area_m2`, `p_before`, `p_after` (средние по пятну), поле `confirmed`, переводит в EPSG:4326.
- `year_pairs`: соседние годы (2019→2020, …) плюс пара "первый→последний", если лет больше двух.
- `confirm_patches`: `confirmed` считается только для пар соседних лет, у которых есть следующий год. Для потери подтверждение = в следующем году средняя P по пятну ниже порога модели; для прироста — не ниже. Средняя берётся **только по пикселям, где в следующем году есть данные**: NaN — это «нет данных», а не «не зелёное». Если данных меньше чем на 50% пятна, или следующего года нет (например 2024→2025 и пара первый→последний), `confirmed = null` («не проверено»). API при `confirmed_only=true` оставляет только `confirmed is True`.

### `aggregate.py`
- `pixel_cells`: для каждого пикселя ищет H3-ячейку (res 8). Ячейка считается на сетке с шагом 5 пикселей и затем "растягивается" на все пиксели (ускорение; на границах гексагонов возможна ошибка порядка десятков метров).
- `zonal`/`compute_zone_stats`: доля зелёных пикселей по годам (`g_{год}`), площади потерь/прироста (`loss_m2_*`, `gain_m2_*`).
- В `h3.geojson` попадают гексагоны минимум с 50 валидными пикселями; считается `delta_pp` (изменение доли зелени за весь период в процентных пунктах).
- Районы: если есть файл `data/boundaries/districts.geojson`, районы растеризуются и считаются теми же функциями. Если файла нет, этот шаг пропускается (в конфиге он помечен как optional).
- `summary.json`: временной ряд по городу, топ-10 горячих точек по потерям, метрики модели.

### `data/download.py`
- `make_geobox`: одна общая сетка (UTM 42N, 10 м) из bbox.
- `open_catalog`: STAC Planetary Computer с подписью ссылок (ключ не нужен).
- `download_s2_year`: сцены за 1 июня–31 августа с `eo:cloud_cover < 30`, берутся 8 самых чистых, затем `composite_from_items`.
- `composite_from_items`: загрузка через `odc.stac`, маска SCL, поправка baseline, медиана.
- `download_worldcover`: берёт тайлы нужной версии продукта (2020 → 1.0.0, 2021 → 2.0.0) и приводит к той же сетке.
- **Исправленный баг:** в `download_s2_year` вызов `write_tif(..., band_names=bands)` использовал неопределённое имя `bands` (падал `NameError` при записи). Исправлено на `im["bands"]`.

### `data/tiles.py`
- `labels_from_worldcover`: green = классы из `green_classes` (10, 20); где WorldCover = 0, метка 255.
- `assign_blocks`: делит сцену на блоки 512 px и случайно (seed фолда) назначает каждому train/val/test в пропорции 0.7/0.15/0.15.
- `split_masks`: попиксельные маски сплитов с буфером: пиксель выкидывается, если ближе 32 px (половина `buffer_px`) к блоку другого сплита. Между сплитами всегда ≥ 64 px «ничейной земли».
- `crop_origins`: все левые верхние углы кропов 256×256, которые **целиком** лежат в train-зоне (без буфера) и где ≥ 50% меток валидны. Проверка за O(1) на окно через интегральное изображение.
- `fixed_tiles`: val/test — тайлы 256×256 без перекрытия, метки вне своей зоны = 255.
- `build_fold` / `main`: для каждого seed из `fold_seeds` (42, 43, 44) пишет `data/tiles/fold{k}/`; для 2020 только `test` (на тех же блоках).

### `data/synthetic.py`
- Генерирует синтетический "Ташкент": классы (деревья, трава, застройка, голая земля, вода), спектры по классам, годы со строительством на зелени и новыми парками, метки "как WorldCover" с шумом.
- `score_change`: сравнивает найденные потери с известными событиями (`event_recall`, `pixel_precision`).
- Зачем: проверить, что весь пайплайн работает и находит заведомо известные изменения. На реальных данных такой проверки в проекте нет, у реальных потерь нет эталона.

### `api/main.py`
- FastAPI, CORS открыт для GET. Эндпоинты: `/api/health`, `/api/meta`, `/api/hexagons`, `/api/districts`, `/api/changes/{kind}/{y0}/{y1}` (фильтры `min_area_m2`, `confirmed_only`), `/api/point` (ряд P(green) по годам в точке), `/` (страница), `/overlays`, `/web`.
- Каталог результатов берётся из переменной `GW_OUTPUTS` (для демо `outputs/demo`).
- Нет аутентификации и базы данных: API только отдаёт готовые файлы.

### `__main__.py`
- CLI-диспетчер. `run_pipeline` = tiles → train → infer → change → aggregate. `demo` накладывает `DEMO_OVERRIDES` (tile 128, block 256, resnet18 без весов, 12 эпох) и после пайплайна вызывает `score_change`.

## 3. Ключевые решения

### 3.1 Облака по SCL, поправка baseline, медианный композит

**Что в коде.** `CLEAR_SCL = [2, 4, 5, 6, 7]` (тёмные области, растительность, голая почва, вода, unclassified). Остальные классы SCL (облака, тени, цирус, снег, насыщенные пиксели, no data) отбрасываются. Поправка: с processing baseline >= 04.00 (2022-01-25) к значениям L2A добавлено смещение +1000 DN. Код вычитает 1000 для таких сцен: `_needs_offset` смотрит на `s2:processing_baseline`, а если его нет — на дату. Затем `/10000`, `clip(0,1)`, медиана по времени (`median("time", skipna=True)`) по ≤ 8 сценам.

**Почему.** Без поправки снимки 2019–2021 и 2022–2025 различались бы по яркости на ~0.1 отражательной способности. NDVI и вся модель увидели бы "изменение", которого нет. Медиана устойчива к остаткам облаков и теней, которые маска пропустила, а летний период (июнь–август) даёт зелень на пике и мало облаков.

**Вопрос:** "Зачем вычитать 1000?"
**Ответ:** В новой версии обработки ESA добавила константу к значениям, чтобы вмещать отрицательные отражения. Если не вычесть, все годы после января 2022 выглядят ярче, и сеть детектировала бы фиктивные изменения. Я выравниваю годы к одной шкале.

**Чего нет.** Нет расширения маски облаков (dilation) и отдельного учёта теней от облаков, кроме того, что делает классификатор SCL. SCL — приблизительный продукт и местами ошибается.

### 3.2 Единая сетка (GeoBox) для всех годов и меток

**Что в коде.** `make_geobox` строится один раз из bbox, CRS EPSG:32642, 10 м. Все годы и все метки загружаются на эту сетку (`odc.stac.load(..., geobox=geobox)`): снимки билинейно, SCL и метки — nearest.

**Почему.** Пиксель (r,c) в 2019, 2025 и в метках — один и тот же участок земли. Тогда сравнение вероятностей по годам — просто вычитание массивов, а тайлы и метки совпадают без дополнительной сшивки. Это условие корректности детекции изменений.

**Вопрос:** "Зачем билинейная интерполяция для бэндов и nearest для SCL?"
**Ответ:** Для классов нельзя усреднять: среднее между "облако" и "вода" не имеет смысла, нужен ближайший сосед. Для отражательной способности усреднение нормально.

### 3.3 Spatial block split (блоки 512 px + буфер 64 px) вместо случайных тайлов

**Что в коде.** `assign_blocks`: блок = `block_size: 512` px (5.12 км), весь блок целиком попадает в train, val или test (0.7/0.15/0.15). Тайл 256 всегда лежит внутри блока (512 кратно 256). `split_masks` дополнительно вырезает буфер 64 px между блоками разных сплитов: пиксели у самой границы train/test — почти дубликаты друг друга, поэтому они не попадают никуда.

**Почему.** Соседние тайлы почти одинаковы (пространственная автокорреляция): один и тот же парк виден в двух соседних тайлах. При случайном разбиении кусок парка в train, а соседний кусок в test, и модель "узнаёт" его, а не обобщает. Метрики завышаются (утечка). Блоки делают тест реально новой территорией.

**Вопрос:** "Почему не случайный split?"
**Ответ:** Из-за пространственной автокорреляции случайные тайлы подсматривают друг у друга. Блочный split честнее: модель оценивается на участках города, которых она не видела.

**История решения (честно).** В первой итерации блок был 1024 px: сцена 2452×2520 px давала всего 3×3 блока, и test состоял из 5 тайлов — метрики почти ничего не значили. Сейчас блок 512 px → 5×5 = 25 блоков, test ≈ 10–12 тайлов на фолд.

**Фолды.** Одно случайное разбиение — это одна «лотерея» блоков. Поэтому разбиение повторяется с тремя seed (42/43/44), и в отчёте — **среднее ± std**. Std показывает, насколько цифра зависит от того, какие районы попали в test. Это repeated spatial split, а не строгий k-fold: test-блоки разных фолдов могут пересекаться.

### 3.4 `test_time`: проверка обобщения во времени

**Что в коде.** `temporal_test_year: 2020`. Для 2020 года нарезаются только test-блоки (те же блоки, что test в 2021), снимки и метки 2020 года. `evaluate_fold` считает на них `test_time/unet` и `test_time/ndvi` в каждом фолде.

**Почему.** Детекция изменений применяет модель к разным годам. Модель обучена на 2021. Если она хорошо работает только в 2021 (на 2020 деградирует), то разница P между годами будет отражать особенности годов (освещение, фенология), а не реальные изменения. `test_time` показывает, переносится ли модель на другой год. Радиометрический jitter и поправка baseline нужны именно для этого.

**Вопрос:** "Как вы знаете, что изменения — не артефакт разных лет?"
**Ответ:** Я отдельно меряю качество на другом годе (2020) на непересекающихся территориях. Если метрики близки к тестовым 2021, модель стабильна во времени. Но это проверка стабильности, а не доказательство точности самих изменений: эталонных карт реальных потерь нет.

**Нюансы.** Метки 2020 (WorldCover v1.0.0) и 2021 (v2.0.0) сделаны разными версиями алгоритма. Часть расхождения — разница версий меток, а не изменения на земле. Проверяются только 2020 и 2021, остальные годы (2019, 2022–2025) без меток.

### 3.5 NDVI-бейзлайн с порогом по лучшему F1 на train

**Что в коде.** `evaluate_fold`: `best_threshold` на NDVI-канале случайной выборки (до 400 тыс.) train-пикселей (сетка 0.05…0.84, шаг 0.01), затем этот порог применяется к val/test/test_time. Результаты в `metrics.json` как `*/ndvi`.

**Почему.** Нужен честный простой контроль. Если U-Net лишь немного лучше "NDVI > порог", то сложная модель не оправдана. Порог бейзлайна подбирается на train (а не на test), чтобы не подгонять под тест, и с лучшим F1 — то есть бейзлайн получает максимум возможного у простого правила.

**Вопрос:** "Зачем U-Net, если есть NDVI?"
**Ответ:** Я это измеряю. NDVI не различает контекст: газон, поле и дерево дают похожий NDVI, а метка WorldCover — именно деревья и кустарник. U-Net использует текстуру и соседей. Цифры сравнения лежат в `metrics.json`, и без этого сравнения утверждать преимущество нельзя. Реальные цифры — в разделе 6.

### 3.6 Loss, аугментации, порог, early stopping

- **Маскированный BCE + Dice (`masked_loss`).** BCE даёт стабильные градиенты на каждом пикселе. Dice оптимизирует перекрытие (близко к IoU), помогает, когда классы несбалансированны (зелени в городе заметно меньше). Пиксели с `255` умножаются на 0 и не участвуют ни в BCE, ни в Dice. Dice здесь считается по всему батчу, со сглаживанием 1.
- **Аугментации.** Поворот на k·90° и отражение (спутниковый снимок не имеет "верха"). Радиометрический jitter: `x * U(0.9,1.1) + N(0, 0.05)` (в нормализованном пространстве) имитирует разницу освещения и фенологии между годами. Это напрямую поддерживает `test_time`.
- **Порог на val.** После обучения `best_threshold` по F1 на val (а не фиксированные 0.5). Модель, обученная с Dice, и шумные метки смещают оптимальный порог. Порог сохраняется в чекпоинт и используется везде (инференс, оверлеи, агрегация).
- **Случайные кропы.** Вместо ~60 фиксированных тайлов каждая эпоха — 500 случайных кропов 256 px из любой точки train-зоны (`RandomCropDataset`). Те же пиксели, но много разных «окон» на них: ~31 шаг за эпоху вместо 4. Val/test остаются фиксированными тайлами, чтобы оценка была воспроизводимой.
- **Early stopping.** По val IoU (при пороге 0.5), `epochs: 40`, `patience: 8`, чекпоинт сохраняется по лучшему IoU. Защита от переобучения под шумные метки.
- **Нюанс.** Early stopping идёт при пороге 0.5, а итоговый порог подбирается позже. Это допустимо, но не идеально.

**Вопрос:** "Почему Dice вместе с BCE?"
**Ответ:** BCE даёт гладкий градиент, Dice напрямую подталкивает метрику перекрытия и устойчив к дисбалансу классов. Сумма проще и стабильнее, чем каждая по отдельности.

### 3.7 IoU, F1, precision, recall

Пусть TP — зелёный и предсказан зелёным, FP — предсказан зелёным, а на деле нет, FN — пропущенная зелень.

- **Precision** = TP/(TP+FP): из того, что назвали зеленью, какая доля правда. Низкая — много ложных тревог.
- **Recall** = TP/(TP+FN): какую долю реальной зелени нашли. Низкий — пропускаем зелень.
- **F1** = 2PR/(P+R) = 2TP/(2TP+FP+FN): гармоническое среднее precision и recall.
- **IoU** = TP/(TP+FP+FN): пересечение / объединение.

Связь: IoU = F1/(2−F1). Пример: F1 = 0.80 → IoU = 0.80/1.20 ≈ 0.67. F1 = 0.90 → IoU ≈ 0.82.

**Почему IoU строже.** В знаменателе IoU ошибки FP и FN считаются один раз к TP, а в F1 TP учитывается дважды, поэтому для любого несовершенного результата IoU < F1. Одна и та же ошибка "наказывается" в IoU сильнее. Для сегментации с малым участком зелени accuracy бесполезна: если 80% города не зелень, модель "всё не зелень" имеет 80% accuracy и нулевой IoU. В коде accuracy считается, но как главная метрика не используется.

**Вопрос:** "Почему не accuracy?"
**Ответ:** Из-за дисбаланса классов. Accuracy награждает за очевидный фон. IoU и F1 смотрят только на класс "зелень" и ошибки вокруг него.

### 3.8 Скользящее окно: перекрытие 50% и Hann-окно

**Что в коде.** `predict_scene`: тайл 256, шаг `tile*(1-0.5)` = 128. Последний ряд/колонка добавляются так, чтобы окно доходило до края (`H - tile`). Для каждого окна вероятность умножается на окно Ханна (`_window`: внешнее произведение `np.hanning`, нижняя граница 1e-3), складывается в `acc`, веса — в `wsum`. Результат `acc / wsum`.

**Откуда швы.** Свёрточная сеть на краю тайла видит меньше контекста (нули за границей), и её предсказание там хуже. Если просто склеить тайлы, на стыках остаются видимые линии: соседние тайлы дают разную вероятность для одних и тех же пикселей у границы.

**Как окно убирает.** Перекрытие 50% означает, что каждый пиксель попадает в несколько окон. Вес Ханна максимален в центре тайла (там предсказание надёжнее) и стремится к нулю на краю. Усреднение с такими весами плавно переходит от одного окна к другому, шва нет, а краевые, менее надёжные предсказания почти не влияют на результат. Минимум весов 1e-3 нужен, чтобы пиксели на самом краю сцены (покрытые одним окном) не получили нулевой вес.

**Вопрос:** "Почему на картах не видно квадратов?"
**Ответ:** Окна перекрываются на 50%, и предсказания усредняются с весом Ханна: центр окна важнее края. Без этого на границах тайлов появляются швы.

**Замечание.** Размер окна при инференсе (`tile_size: 256`) совпадает с размером обучения, это сознательно.

### 3.9 Гистерезис, морфологическое открытие, минимальная площадь, `confirmed`

**Что в коде.** Потеря: P(до) >= thr + 0.15 и P(после) <= thr − 0.15, где thr — порог модели из чекпойнта (подобран на val). Между ними — "серая зона", её не считаем ни потерей, ни зелёным. Затем открытие (`opening_iterations: 1`), удаление пятен < 500 м² (5 px), поле `confirmed`.

**Почему от порога модели, а не 0.6/0.3.** Если модель считает зелёным P ≥ 0.65, то фиксированные 0.6/0.3 противоречат карте: пиксель с P = 0.62 «уверенно зелёный» для детектора изменений, но не зелёный на карте. Отступы от thr делают карту, статистику и полигоны согласованными.

**Почему.**
- Один порог (например, 0.5) даёт "мерцание": пиксель с P = 0.51 в одном году и 0.49 в другом считался бы потерей. Два порога требуют уверенно зелёного "до" и уверенно не зелёного "после".
- Открытие убирает одиночные пиксели и тонкие нитки (шум по границам объектов).
- Минимальная площадь отсекает мелкие пятна, которые при 10 м всё равно ненадёжны.
- `confirmed`: потеря подтверждена, если в следующем году участок тоже не зелёный. Разовые артефакты (облачный композит, засушливое лето) обычно не держатся два года подряд. Считается только по пикселям с данными; если данных мало или следующего года нет — `null`, то есть «не проверено», а не «подтверждено» (см. модуль `change.py`).

**Вопрос:** "Как вы отличаете вырубку от сезонности?"
**Ответ:** Полностью — не отличаю. Я беру один сезон (лето) каждый год, использую двойной порог, чистку мелких пятен и подтверждение по следующему году. Это снижает ложные срабатывания, но не гарантирует: нужен контроль по снимкам высокого разрешения или полевая проверка.

### 3.10 H3-гексагоны vs административные районы

**Что в коде.** Основная агрегация — H3 resolution 8 (≈0.74 км² на ячейку). Районы — опциональный дополнительный слой, если есть `data/boundaries/districts.geojson` (поле `name`).

**Почему гексагоны.**
- Одинаковая форма и площадь: доли зелени сопоставимы между ячейками. Районы сильно различаются по площади, и "доля по району" скрывает локальные очаги потерь.
- Не зависят от изменения административных границ и их доступности (файла границ в проекте может не быть).
- Соседи равноудалены, удобно для карты и поиска горячих точек.

**Почему районы тоже нужны.** Решения принимают и отчитываются по районам (хокимиятам), поэтому слой подключён как опция. Реального файла границ в репозитории может не быть; без него пункт просто пропускается.

**Вопрос:** "Почему не районы?"
**Ответ:** Районы — разные по размеру единицы, и среднее по району прячет локальные потери. H3 даёт равные ячейки для сравнения и поиска горячих точек. Районы доступны как дополнительный слой, когда есть геометрия.

## 4. Честные ограничения

1. **10 м — это зоны, а не отдельные деревья.** Пиксель 10×10 м смешивает крону, асфальт, газон. Одиночные деревья и узкие аллеи (в синтетике это учтено: "tiny events are below the 10 m detection limit") модель увидеть не может. Результат — доля озеленённой территории, а не инвентаризация деревьев.
2. **WorldCover — шумная метка, а не эталон.** Заявленная общая точность продукта ≈ 75–77%. Мы учим модель на метках, которые сами ошибаются, и меряем качество против тех же меток. Поэтому метрики сверху ограничены качеством меток: даже идеальная модель не получит 100%, а высокие значения могут означать, что модель повторяет ошибки метки. Для честной оценки нужна выборка вручную размеченных участков (в проекте её нет).
3. **Метки разных лет сделаны разными версиями (v1.0.0 и v2.0.0).** Часть различий между 2020 и 2021 — разница алгоритма.
4. **Потеря зелени != нарушение.** Метод видит только, что зелени стало меньше. Была ли вырубка законной, плановой (реконструкция, посадка по проекту) или нарушением, можно узнать только сопоставив с реестром разрешений и документами. Таких данных в проекте нет. В отчёте корректно говорить "кандидаты на проверку", а не "нарушения".
5. **Сезонность, полив, облака.** Берётся лето (июнь–август). Засуха, ограничение полива или раннее пожелтение газонов снижают P(зелень) без реальной потери. Облака маскируются по SCL, но при ≤ 8 сценах и без расширения маски остатки теней возможны. Композит усредняет сезон и не фиксирует точную дату изменения: это "между годом A и годом B".
6. **Мало блоков.** 25 блоков и 3 фолда — это уже оценка разброса (± std), но не полноценные доверительные интервалы; test-блоки фолдов могут пересекаться.
7. **Нет проверки изменений на реальных данных.** Качество детекции изменений проверено только на синтетике (`score_change`). На реальном Ташкенте эталонных потерь нет.
8. **Технический баг `bands` в `download_s2_year`** исправлен (`im["bands"]`).
9. **Нет:** тестов на независимой карте, оценки неопределённости, учёта теней, привязки к кадастру, мониторинга в реальном времени.

## 5. Шпаргалка: 10 вопросов и ответы

1. **Что делает проект?** Сегментирует зелёный покров Ташкента по Sentinel-2 нейросетью U-Net, находит потери и прирост зелени между годами 2019–2025 и показывает на карте с гексагонами H3.
2. **Откуда данные и метки?** Снимки Sentinel-2 L2A и ESA WorldCover из STAC Planetary Computer (бесплатно, без ключа). Зелень = классы 10 (деревья) и 20 (кустарник).
3. **Почему 8 каналов?** 6 бэндов (B02, B03, B04, B08, B11, B12) + NDVI + NDBI: индексы дают готовый сигнал о растительности и застройке.
4. **Как боретесь с облаками и разными годами?** Маска по SCL, поправка −1000 DN для baseline >= 04.00 (с 2022-01-25), медиана до 8 сцен за лето, единая сетка.
5. **Как оценивали честно?** Блочный split (512 px) с буфером 64 px исключает утечку соседних пикселей; 3 фолда дают среднее ± std. Плюс `test_time` на 2020 — проверка переноса во времени. Плюс сравнение с NDVI-порогом.
6. **Почему IoU, а не accuracy?** Класс зелени меньше фона, accuracy обманчива. IoU = TP/(TP+FP+FN) строже F1, связь IoU = F1/(2−F1).
7. **Как убираете швы?** Скользящее окно 256, перекрытие 50%, усреднение с весом Ханна: центр окна надёжнее края.
8. **Как определяете потерю?** P >= thr+0.15 до и P <= thr−0.15 после (гистерезис вокруг порога модели), открытие, минимум 500 м², флаг `confirmed` по следующему году (null, если проверить нечем).
9. **Почему гексагоны?** Равные ячейки (~0.74 км², res 8) — сравнимые доли и горячие точки; районы — опциональный слой, когда есть границы.
10. **Главные ограничения?** 10 м — это зоны, не деревья; WorldCover ~75–77% точности, метрики ограничены качеством меток; потеря зелени не равна нарушению без данных о разрешениях; сезонность, полив, облака дают ложные сигналы.

- *Сравнивать итерации напрямую нельзя.* Тестовые выборки разные. Поэтому сравниваю разницу U-Net − NDVI на одних и тех же тайлах: была −0.04, стала +0.16.
